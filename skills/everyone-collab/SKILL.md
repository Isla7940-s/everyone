# Everyone 跨端协同（标准 Skill）

你是用户本地的 AI Agent（运行在 Codex / Cursor / Claude Code 等工具里）。本 Skill 指导你把用户的本地工作记录同步到 Everyone 云端，并配合远程协作。所有云端交互都通过 **Everyone CLI**：

```bash
node ~/.everyone/everyone.mjs <命令>     # 以下简写为 everyone <命令>
everyone auth status                     # 任何操作前先验证配置（未配置时引导用户 auth login）
```

## 铁律（先读）

1. **授权范围**：只读用户明确允许的工具、项目/工作区、会话。用户没说允许的，一律不读、不猜、不默认。首次使用先问清楚：允许读哪些工具？哪些项目？是否允许上传总结？是否允许本地客户端执行远程协作？把用户的决定记下来（写进你的记忆/本地配置），之后严格遵守。
2. **隐私**：云端只上传**总结**（25 字短总结 + 100 字详细总结 + 元数据），永远不上传聊天原文、代码原文、密钥。原文只留在本地。
3. **先确认后上传**：任务完成、时间去向属于正式数据，必须先把草稿展示给用户，用户明确回复"没问题/确认/可以"之后，才允许带 `--confirmed` 调用 CLI 正式上传。工作会话总结可以在授权范围内直接上传。

## 一、识别工作会话

一段本地 AI 聊天 = 一个工作会话。判断标准：围绕一件具体工作展开（写代码/写文档/查数据/调试等），有实际产出或结论。闲聊、测试性提问不算。

各工具的会话记录位置（只在用户授权后读取）：

| 工具 | 会话记录位置 |
| --- | --- |
| Codex | `~/.codex/sessions/**/*.jsonl` |
| Claude Code | `~/.claude/projects/<项目>/*.jsonl` |
| Cursor | `~/.cursor/projects/<项目>/agent-transcripts/*.jsonl` |

## 二、生成统一格式的工作总结

每个工作会话生成：

- **大需求名称**（≤20 字）：这件事属于哪个大目标，如「支付系统升级」
- **子任务名称**（≤20 字）：具体做的哪一块，如「支付回调重试」
- **25 字短总结**：一句话说清做了什么、结果如何
- **100 字详细总结**：做了什么、怎么做的、结论/产出、遗留问题
- 会话时间、来源工具、（可选）关联任务 ID

**命名规则（重要，时间穿透靠它聚合）**：同一个大需求在不同会话里必须用**完全相同**的名称；同一个子任务同理。上传前先查已有命名：

```bash
everyone sessions list --limit 30        # 看已有的大需求/子任务叫什么，能归入就完全复用
```

拿不准名称是否与已有需求一致时，先把候选名称展示给用户确认或修改，再上传。

上传（同时登记本地映射，云端 Agent 才能对这个会话发起远程求助）：

```bash
everyone sessions upload --tool codex \
  --requirement "支付系统升级" --subtask "支付回调重试" \
  --brief "实现回调重试机制并补齐单测" \
  --detail "在 webhook 处理层加入指数退避重试（最多5次），失败落死信表；补充单测12个全部通过；遗留：死信表报警未接。" \
  --at "2026-08-29T15:00:00+08:00" \
  --local-path ~/.codex/sessions/2026/08/29/rollout-xxx.jsonl
```

不传 `--id` 时云端会生成 16 位字母数字会话 ID 并返回，记住它用于后续关联。

## 三、任务和排期

```bash
everyone tasks list            # 我的未完成任务（状态/截止时间/关联信息）
everyone tasks schedule        # 排期视图（按截止时间）
everyone tasks get <taskId>    # 单个任务详情
```

做工作总结时，若会话对应某个云端任务，用 `--task <taskId>` 关联。

## 四、任务完成（草稿 → 用户确认 → 正式上传）

判断任务完成的标准：任务要求的产出已存在且可验证（代码已改并通过验证 / 文档已成稿 / 数据已交付），没有阻塞性遗留。

```bash
# 1. 生成拟上传内容并上报草稿（不改任务状态；--attach 上传产出物/证据文件，逗号分隔多个）
everyone tasks complete-draft t-xxxx \
  --note "回调重试已上线：指数退避最多5次，失败落死信表；单测12个全过" \
  --leftover "死信表报警待接入" \
  --sessions ABCD2345EFGH6789 \
  --attach 变更报告.md,测试输出.png

# 2. 把草稿内容展示给用户：对应任务、关联会话、完成说明、产出物、遗留问题
# 3. 用户回复"没问题"或等价确认后，才执行：
everyone tasks complete t-xxxx --confirmed
# 上传成功后云端自动把任务标记为完成，并保存完成说明、关联会话与附件证据
```

## 五、时间去向（草稿 → 用户确认 → 正式上传）

可以在日常心跳/收尾时整理当天时间去向：

```bash
everyone time draft --date 2026-08-29 > /tmp/time-draft.json   # 基于当天已上传会话生成草稿
# 编辑草稿：每条含 大需求/子任务/关联会话/开始结束时间或时长/简短与详细总结
# 展示给用户（日期、每项工作、时长），用户确认后：
everyone time submit --file /tmp/time-draft.json --confirmed
```

同一天重复上传会整体替换，放心修正。

## 六、配合远程求助

云端 Agent 缺上下文时会发起远程求助，由**本地客户端**（everyone_local_client.py）接收并处理——它根据会话 ID 找到原始会话、建沙箱、启动本地 Codex。你的职责：

- 上传总结时尽量带 `--local-path`，映射登记了求助才能还原原文；
- 用户问起时可查询：`everyone help list`（待处理）/ `everyone help status <helpId>`（执行状态）；
- 本 CLI **没有**「提交回复/上传附件」能力——那两项只存在于求助沙箱内的精简 CLI 里，不要在这里找。

## 七、日常节奏建议

1. 完成一段有产出的工作 → 按第二节上传该会话总结（授权范围内直接传）；
2. 会话能对应云端任务 → 顺手判断任务是否完成，完成则走第四节草稿+确认流程；
3. 每天收尾（或用户要求时）→ 走第五节时间去向草稿+确认流程。
