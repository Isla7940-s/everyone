# Skill: 缺陷报告

> 报 UI/前端缺陷时用。产出一份接手的人零追问就能开工的报告：能复现、有环境、知道多严重。

## 成稿骨架（直接套用）

```markdown
# 【页面】【现象】【条件】（例：登录页在低端机上首屏加载 > 5s）

- 严重级：P0 阻断 / P1 主流程受损 / P2 体验问题 / P3 视觉瑕疵
- 复现率：必现 / 高频（7/10）/ 偶现（2/10，附出现时间点）

## 复现步骤
1. 冷启动 App，进入【入口】
2. 【具体操作，谁按着做都能复现】
3. 观察【哪里】

## 预期 vs 实际
- 预期：【应该看到什么，引用设计稿/规范条目】
- 实际：【实际看到什么】（截图见附件，看【哪个区域】）

## 环境
| 机型 | 系统 | App 版本 | 网络 |
| --- | --- | --- | --- |
| Redmi 9A | Android 11 | 3.2.1 | Wi-Fi |

## 影响面与线索
- 影响：【哪些用户、估个量级、影响什么指标】
- 线索：【怀疑 XX（依据是…），待确认】/ 没有线索就写「无，未定位」
```

## 写作规则

- 一个报告只报一个问题；发现三个问题就拆三份，别打包
- 标题必须让人不点开就知道是什么事（页面 + 现象 + 条件）
- 复现步骤从冷启动写起；偶现问题附最近一次出现的精确时间（方便查日志）
- 「预期」优先引用设计规范条目（规范 2.0：主色 #3370FF / 圆角 8px / 间距 4 的倍数），不引用就贴设计稿链接
- 严重级和复现率是分派优先级的依据，不许空着；拿不准严重级就按影响的用户量级判

## 好坏对照

- ❌ 「首页有时候会卡」
- ✅ 「首页信息流在 Android 低端机滑动掉帧（Redmi 9A 实测 22fps），高频 7/10，怀疑列表项过度重绘（滚动时 GPU 呈现模式全红）」

## 交稿自查

- [ ] 标题 = 页面 + 现象 + 条件
- [ ] 步骤可复现、有复现率
- [ ] 预期引用了规范或设计稿
- [ ] 环境四件套齐全
- [ ] 严重级 + 影响面已填，猜测都标注了「怀疑/待确认」
