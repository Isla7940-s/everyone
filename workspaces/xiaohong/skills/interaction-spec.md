# Skill: 交互说明

> 把一个界面交给前端实现时用。产出一份「开发照着做不用来问」的说明：每种界面状态长什么样、什么条件下切换。

## 成稿骨架（直接套用）

```markdown
# 【页面 / 组件名】交互说明（设计稿：【链接】｜ 规范 2.0）

## 这个界面解决什么
【一句话：用户在什么场景下来到这里，要完成什么】

## 界面状态（每种都要有）
| 状态 | 触发条件 | 界面表现 | 用户可做的操作 |
| --- | --- | --- | --- |
| 默认 | 【条件】 | 【展示什么】 | |
| 加载中 | 请求发出 > 300ms | 骨架屏（不用转圈） | 可返回 |
| 空 | 返回 0 条 | 插图 + 【文案】+ 【主按钮】 | 【引导去哪】 |
| 出错 | 请求失败 / 超时 | 【文案：告诉用户怎么办】+ 重试按钮 | 重试、返回 |
| 极限 | 标题 > 20 字 / 列表 > 500 条 | 【怎么截断、怎么分页】 | |
| 无权限 | 【条件】 | 【文案】 | 【去申请】 |

## 关键流程
1. 用户【操作】→ 界面【变化】→ 【结果】
2. 中途返回 / 杀进程再进来：【是否保留填写内容】

## 规格
- 主色 #3370FF｜圆角 8px｜间距取 4 的倍数（规范 2.0）
- 字号 / 行高：【标注】｜ 点击热区不小于 44×44
- 动效：【时长 / 缓动】，低端机降级为无动效

## 边界与降级
- 弱网（3s 未返回）：【怎么表现】
- 暗色模式：【差异说明】，文字对比度 ≥ 4.5:1
- 长文本 / 多语言：【怎么处理换行与截断】
```

## 写作规则

- 六种界面状态（默认、加载、空、出错、极限、无权限）一个都不能省，确实不存在的写「不适用：原因」
- 每种状态必须写触发条件，只描述长相不写条件等于没写
- 错误态文案必须告诉用户「怎么办」，不写「加载失败」了事
- 所有尺寸、颜色、间距引用规范 2.0 的条目，规范里没有的才标具体值并说明为什么例外
- 不用「更好的体验」「更流畅」这类形容词，改成用户能感知的具体描述
- 动效和暗色模式都要给降级方案

## 好坏对照

- ❌ 「列表页加载时显示 loading，加载失败给个提示，整体体验要流畅自然。」
- ✅ 「加载中：请求超过 300ms 才显示骨架屏（3 条占位卡片），避免快速返回时闪一下。出错：显示『没能加载出来，检查下网络？』+『重试』按钮，重试保留原滚动位置；连续失败 3 次改为『稍后再试，我们正在修复』并隐藏重试按钮。」

## 交稿自查

- [ ] 六种界面状态齐全，每种都有触发条件
- [ ] 错误态文案告诉了用户怎么办
- [ ] 规格引用了规范 2.0 条目
- [ ] 写了弱网、暗色模式、长文本三类边界
- [ ] 全文没有无法验收的形容词
- [ ] 中途退出的状态保留规则已说明
