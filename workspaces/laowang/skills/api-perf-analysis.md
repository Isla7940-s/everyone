# Skill: 接口性能分析

> 分析某个接口 / 某段链路变慢时用。产出「结论 → 依据 → 风险」三段式的分析，数字必须能被别人复现。

## 成稿骨架（直接套用）

```markdown

## 现状数据

| --- | --- | --- | --- |

| P99 | | | |
| QPS | | | |
| 错误率 | | | |

- 数据来源：【监控看板 / 日志表】｜ 统计窗口：【时间段】｜ 样本量：【N】

## 耗时拆解
| 阶段 | 耗时 | 占比 | 说明 |
```

## 写作规则

- 先给数字后给观点，观点必须能从上面的数字推出来
- 耗时拆解各阶段之和要与总耗时对得上，对不上的部分标成「未归因 xx ms」
- 所有数据写清楚来源、统计窗口、样本量；抽样的要标注抽样比例
- 收益是估算就写「估算」并写出假设（「假设缓存命中率 80%」）
- 必须写排除项，让人知道哪些方向已经查过了
- 结尾固定「结论 → 依据 → 风险」三段
- 对齐服务端 SLA：可用性 99.9%，P95 < 300ms

## 好坏对照

- ❌ 「接口比较慢，主要是数据库查询耗时较长，建议加缓存优化。」
- ✅ 「结论：耗时集中在订单列表的 DB 查询，占 P95 的 68%（214ms / 315ms，来源 APM，8/25~8/27，样本 42 万次）。根因：`order_list` 走了 `idx_uid` 后回表，单次扫 3.2 万行（explain rows=32k，实测慢日志均值 208ms）。排除了下游 RPC（P95 18ms，无毛刺）和序列化（9ms）。方案：加 (uid, status, created_at) 联合索引，估算 P95 降到约 110ms（假设回表消除、其余阶段不变），成本 0.5 人日，风险是写入放大约 3%，上线后盯 24h 的写 P99。」
