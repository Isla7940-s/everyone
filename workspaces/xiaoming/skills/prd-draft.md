# Skill: PRD 草案

> 写需求文档草案时用。产出一份评审会上能直接过的 PRD 初稿：问题有数据、目标可量化、方案有状态图、边界写清楚。

## 成稿骨架（直接套用）

```markdown
# 【需求名】PRD v0.1

## 1. 背景与问题
【一段话：什么问题、影响多少用户、什么口径。例：注册流程验证码到达率 87%（8 月口径，短信通道 A），
每天约 400 名新用户卡在验证码步骤流失，占注册流失的 31%。】

## 2. 目标与非目标
- 目标：【可量化，如「注册转化 41% → 45%，上线后两周内」】
- 非目标：【这期明确不做的，如「不动登录流程；不做语音验证码」】

## 3. 方案概述（用户视角）
【入口 → 界面 → 操作 → 反馈，逐步写。每个界面列出全部状态：】
- 默认态：【用户看到什么】
- 加载态：【超过 3s 显示什么】
- 失败态：【提示什么、用户能做什么】
- 空态 / 边界：【首次 / 无网络 / 重复提交】

## 4. 埋点与验收
| 埋点 | 触发时机 | 用来回答什么问题 |
| --- | --- | --- |
- 验收标准：【上线 N 天后看什么数，达到多少算成功，不达标怎么办（回滚/迭代）】

## 5. 依赖与排期
- 设计（小红）：【要什么、什么时候要】
- 服务端（老王）：【要什么、什么时候要】
- 里程碑：设计稿 MM/DD → 联调 MM/DD → 灰度 MM/DD → 全量 MM/DD
```

## 写作规则

- 问题必须用数据定量（影响面、口径、来源），「用户反馈不好」不算问题描述
- 每个方案给「最小可上线版本」，砍掉的功能放「后续迭代」一节，不许堆在主方案里
- 界面状态必须穷举（默认/加载/失败/空态），这是小红评审的第一关
- 涉及登录/注册链路的改动，必须写对已知问题（空白页、验证码、低端机加载）的影响
- 时间承诺留缓冲；所有依赖要有兜底（「短信通道 B 未就绪则先上通道 A 重试逻辑」）

## 好坏对照

- ❌ 目标：「优化注册体验，提升转化」
- ✅ 目标：「注册转化 41% → 45%（上线两周内，口径：完成注册/进入注册页）」
- ❌ 「异常情况给出友好提示」
- ✅ 「验证码 60s 未达：提示『可能被拦截，试试语音验证码』，按钮切换为『语音接听』」

## 交稿自查

- [ ] 问题一段话里有数字、口径、来源
- [ ] 目标可量化、非目标至少 2 条
- [ ] 每个界面四态齐全
- [ ] 埋点表能回答验收问题
- [ ] 谨叔视角过一遍：绝对化承诺、没有预案的「万一」都补掉
